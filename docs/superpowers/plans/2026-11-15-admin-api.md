# Admin API (Phase 2 backend) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Add the authenticated `/admin/*` API and the `/partner/:token/*` link API to the C2V bot server, so the
Next.js vendor dashboard can run every vendor operation without touching the database, Cashfree or Meta.

**Architecture:** New `src/admin/` feature folders (auth, orders, customers, catalog, partners, settings, chats)
plus `src/partner/`, each a Hono sub-app mounted in `buildApp`. A bearer-session middleware resolves
`vendor_sessions → tenant` and puts the `TenantConfig` on the context. Handlers call tenant-scoped repos and the
existing `updateStatus` / `refundOrder` / `sendAndLog`. One error mapper turns domain errors into the contract's
`{ error: { code, message } }`.

**Tech Stack:** existing: Node 22, TypeScript strict, Hono, drizzle-orm + postgres-js, zod 4, vitest + PGlite,
pino. Password hashing with `node:crypto` scrypt (no new dependency).

**Spec:** `docs/admin-api.md` (the API contract; every path, body, response shape and error code is defined
there). Background: `docs/phase2-dashboard-brief.md`.

## Global Constraints

- Every path, field name, status code and error `code` matches `docs/admin-api.md` exactly. If a task finds the
  contract wrong, change the contract in the same commit and say so in the report.
- Tenant comes only from the session (`c.get('tenant')`). No route reads a tenant id from path, query or body.
  Every query filters `tenant_id`. Another tenant's id behaves exactly like a missing id (404 `not_found`).
- Reuse, never re-implement: status changes go through `updateStatus`, refunds through `refundOrder`, outbound
  WhatsApp through `sendAndLog` (all existing).
- Money is integer paise. Timestamps are serialised as ISO strings. Phones are `91XXXXXXXXXX`.
- Request validation with zod (`safeParse`). Failures → 400 `validation_error` with `details: {path, message}[]`.
- Secrets/tokens never logged: no session tokens, partner tokens, passwords or password hashes in logs or
  error messages.
- No new runtime dependencies. No new env vars.
- Schema changes go through `pnpm db:generate` (drizzle-kit); new tables get `.enableRLS()` (the existing
  `tests/db/rls.test.ts` checks every table automatically).
- Session tokens and partner tokens are `randomBytes(32).toString('base64url')` (43 chars). Session tokens are
  stored as sha256 hex. Partner tokens are stored as-is (decision: vendor can re-copy the link).
- Session lifetime 30 days, fixed. Expired sessions are rejected and deleted when presented. No cron job.
- Password hash format: `scrypt$<N>$<r>$<p>$<saltB64url>$<hashB64url>` with N=16384, r=8, p=1, 16-byte salt,
  64-byte key. Verify with `timingSafeEqual`. (scrypt instead of the brief's argon2/bcrypt: built in, no native dependency.)
- Usernames are stored lowercased and trimmed; unique across tenants.
- Tests use `buildApp(testDeps({ db, ... }))` + `app.request(...)` against PGlite, with tenants `test` and
  `other` registered (`testTenant()`, `testTenant({ id: 'other', waPhoneNumberId: 'other-phone' })`).
- User workflow: stop after each task for review; commit only after approval; commit messages 2–3 lines; run
  `bash .superpowers/secret-check.sh` (must print nothing) before each commit.

## Review Focus

1. **Cross-tenant access:** a `test` session asking for an `other` order/customer/product/pincode/partner/chat id →
   404, and lists never include `other` rows. Each resource task carries this test.
2. **Partner link scope:** a valid token must not act on an order assigned to another partner, or one that was
   reassigned away. An inactive partner's token → 404. (Task 7)
3. **Password change / deactivate actually revokes:** old tokens → 401 right after. (Task 2)
4. **Refund provider failure:** Cashfree error → 502 `provider_error`, order and payment unchanged. (Task 4)
5. **9th active product** via POST *or* PATCH `active: true` → 409, and re-saving an already active product
   doesn't count itself twice. (Task 6)
